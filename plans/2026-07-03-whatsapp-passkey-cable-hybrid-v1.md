# WhatsApp Passkey caBLE / WebAuthn Hybrid Authenticator

## Objective

Replace chat-cli's non-working self-minted software WebAuthn credential (`crates/providers/whatsapp/go/passkey.go`) with a real **WebAuthn hybrid transport (caBLE / CTAP 2.2 hybrid) CLIENT** implemented inside the Go bridge. In the hybrid ceremony chat-cli acts as the WebAuthn *client/companion* that publishes a caBLE QR; the user's phone acts as the *authenticator* that scans the QR over BLE and signs WhatsApp's challenge with the phone's real account passkey. The signed assertion is delivered back to whatsmeow via `cli.SendPasskeyResponse`, which lets the server emit the `primary_ephemeral_identity` continuation and complete device linking.

### Why this is required (ground truth)
- The current self-minted assertion IS accepted at the IQ level (`<iq type="result"/>`), but the phone never sends the continuation, so linking stalls. Confirmed in `tmp/debug.log` (two runs).
- Server challenge observed: `allowCredentials=[]`, `rpId=whatsapp.com`, `userVerification=required`, `extensions={uvm:true}`.
- Phone UI displays "Continue on your other device… You may need to scan another QR code to use your passkey," proving WhatsApp expects the WebAuthn hybrid/caBLE transport, not an unregistered software credential.
- Environment already validated: Chromium 148 + Firefox present; BlueZ healthy (Intel `hci0` UP/RUNNING, `bluetoothd` active, D-Bus up); tunnel servers `cable.ua5v.com` and `cable.auth.com` reachable; Go toolchain builds/vets clean. OS: Slackware-based NimbleX live distro.

### Non-goals
- No changes to whatsmeow itself (pinned `v0.0.0-20260630180629-b572e5bcb92b`).
- No cross-platform BLE (Linux/BlueZ only for the first delivery; other OSes keep a clear "unsupported" error path).
- No attempt to register a new passkey — the phone already holds the account passkey; we only drive an assertion (CTAP `getAssertion`).

## Design Overview

The hybrid CLIENT ceremony (CTAP 2.2 §11.5 "hybrid transports") performed by chat-cli:

1. Generate an ephemeral P-256 client keypair and a 16-byte QR secret; encode a `FIDO:/` base10 caBLE QR (CBOR map: client public key, secret, assigned tunnel-domain hint, timestamp, `state-assisted-tx` flag, operation hint = `ga`/get-assertion). Emit it to the UI.
2. The phone scans the QR, then BLE-advertises a 16/20-byte encrypted advert. Scan BLE, decrypt with the EID key derived from the QR secret, obtaining the assigned tunnel-server index (24-entry assigned domain list), routing ID, and BLE nonce.
3. Open a `wss://cable.<domain>/cable/connect/<routing-id>/<tunnel-id>` WebSocket with the FIDO caBLE subprotocol.
4. Run a Noise `KNpsk0` handshake (Curve25519 + HKDF-SHA256 + AES-256-GCM) with a PSK derived from QR secret + BLE nonce; then frame CTAP2 messages over the encrypted channel.
5. Send a CTAP2 `authenticatorGetAssertion` (CBOR) built from the whatsmeow-provided `challenge` / `rpId` / `allowCredentials` / `userVerification`. Parse `authenticatorData`, `signature`, `credentialId`, `userHandle` from the phone's response.
6. Map into `types.WebAuthnResponse` and call `cli.SendPasskeyResponse`; keep the tunnel and pairing connection alive through the continuation/confirmation stages.

### New Go files (all under `crates/providers/whatsapp/go/`)
- `cable_qr.go` — QR secret + client keypair generation, `FIDO:/` base10 CBOR payload construction, EID-key derivation helper.
- `cable_ble.go` — BlueZ/D-Bus BLE scanner, advert capture, advert decryption → tunnel index + routing + nonce.
- `cable_tunnel.go` — WebSocket dial + FIDO caBLE subprotocol, tunnel-domain resolution from the 24-entry assigned list.
- `cable_noise.go` — Noise `KNpsk0` state machine (Curve25519/HKDF-SHA256/AES-256-GCM) and post-handshake message crypt.
- `cable_ctap.go` — CTAP2 CBOR request/response for `getAssertion`; mapping helpers to `types.WebAuthnResponse`.
- `cable_session.go` — orchestration: ties QR→BLE→tunnel→noise→ctap→SendPasskeyResponse into one cancellable ceremony; owns per-phase `emit`/`c.log`; env overrides.
- `passkey.go` — modified: `handlePasskeyRequest` delegates to `cable_session` instead of `buildWebAuthnAssertion`.
- Test files: `cable_qr_test.go`, `cable_noise_test.go`, `cable_ctap.go` vectors in `cable_ctap_test.go`, `cable_ble_test.go` (decrypt vectors).

## Potential Risks and Mitigations

1. **BLE permissions/capabilities on the NimbleX live distro.**
   Mitigation: use BlueZ over D-Bus (session/system bus) rather than raw HCI sockets to avoid `CAP_NET_ADMIN`; environment findings confirm `bluetoothd` active and `hci0` UP/RUNNING. Provide `CHATCLI_WHATSAPP_CABLE_BLE_ADAPTER` override and a clear error if discovery is denied. Document that running as the same user as `bluetoothd`'s D-Bus policy allows is required.
2. **Tunnel-domain derivation correctness (24-entry assigned list).**
   Mitigation: unit-test the index→domain function; special-case the two confirmed-reachable domains (`cable.ua5v.com`, `cable.auth.com`); expose `CHATCLI_WHATSAPP_CABLE_TUNNEL_DOMAIN` to pin a domain during live bring-up.
3. **whatsmeow handoff-proof interaction / clientDataJSON mismatch.**
   Mitigation: keep the clientDataJSON that produced the CTAP clientDataHash byte-identical to the one placed in `WebAuthnResponse` (Task 6.1); leave `handlePasskeyConfirmation` (`crates/providers/whatsapp/go/passkey.go:139`) untouched so whatsmeow's auto-confirm/handoff-proof logic (`/root/go/pkg/mod/go.mau.fi/whatsmeow@.../pair-passkey.go:117-140`) is unaffected; assert mapping via unit vectors.
4. **WhatsApp's hybrid variant deviates from standard CTAP caBLE.**
   Mitigation: heavy per-phase hex-dump instrumentation (`CHATCLI_WHATSAPP_CABLE_DUMP`); isolate deviation to a single layer (QR/advert/tunnel/noise/ctap) via layered unit tests; keep each layer's constants (salts, info strings, service UUID, subprotocol) in one place for quick adjustment; retain legacy path for comparison. If the phone's authenticator turns out to be a *platform* (not hybrid) authenticator that only exposes hybrid via the OS, escalate to capturing a Chromium 148 caBLE session (present in env) as a reference transcript.
5. **Connection lifetime: emitter/tunnel closing mid-ceremony.**
   Mitigation: Task 7.1 audit + hold-open; store session handles on `client` (`crates/providers/whatsapp/go/bridge.go:46`) and only tear down on confirmation/connected/cancel.
6. **cgo build breakage on macOS/Windows from BLE/DBus deps.**
   Mitigation: Linux build tag gate (Task 0.4) so `cable_ble.go`/DBus code compiles only on Linux; a stub returns an explicit unsupported error on other OSes, keeping `build.rs` archive builds green (`crates/providers/whatsapp/build.rs:31-45`).

## Alternative Approaches

1. **Implement the caBLE client outside Go (in Rust or via an external helper such as `libfido2`/`chromium --enable-features`).** Trade-off: Rust has BLE crates (`btleplug`) and could own the ceremony, but the assertion must still cross back into the Go bridge to reach `SendPasskeyResponse`, adding an FFI round-trip and a second async runtime. Keeping it in Go co-locates it with whatsmeow and the existing event pipeline. Rejected for MVP.
2. **Drive a real browser/OS authenticator (headless Chromium 148, present in env) to perform WebAuthn and scrape the assertion.** Trade-off: reuses a battle-tested caBLE implementation and sidesteps hand-rolled crypto, but requires WhatsApp's web origin/session context, browser automation plumbing, and is fragile across Chromium updates. Useful as a *reference transcript* generator (see Risk 4) but not as the shipping path.
3. **Ask WhatsApp/whatsmeow for a non-passkey linking path (older multi-device protocol).** Trade-off: zero new crypto, but the server now mandates the passkey stage (ground-truth findings), so this is not available. Rejected.
4. **Single monolithic `cable.go` instead of layered files.** Trade-off: fewer files, but far harder to unit-test each layer and to localize WhatsApp-specific deviations. Rejected in favor of the layered module split.
