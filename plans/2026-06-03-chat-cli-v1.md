- **`provider.rs` — the `Provider` trait:**

```rust
use async_trait::async_trait;
use tokio::sync::broadcast;
use crate::types::*;

#[async_trait]
pub trait Provider: Send + Sync + 'static {
    /// Stable identifier for this account instance (e.g. "whatsapp:+1234567890")
    fn id(&self) -> &ProviderId;
    fn platform(&self) -> Platform;
    fn account_info(&self) -> Account;

    /// Connect / authenticate. Emits AuthRequired event if credentials needed.
    async fn connect(&self) -> anyhow::Result<()>;
    async fn disconnect(&self) -> anyhow::Result<()>;
    fn is_connected(&self) -> bool;

    /// Subscribe to real-time events from this provider
    fn events(&self) -> broadcast::Receiver<ProviderEvent>;

    /// Enumerate all chats (contacts + groups + channels). May return cached data immediately.
    async fn chats(&self) -> anyhow::Result<Vec<Chat>>;

    /// Load message history. `before` enables pagination (pass oldest known timestamp).
    async fn history(
        &self,
        chat_id: &ChatId,
        before: Option<Timestamp>,
        limit: usize,
    ) -> anyhow::Result<Vec<Message>>;

    /// Send a message. Returns the sent message's ID.
    async fn send(
        &self,
        chat_id: &ChatId,
        content: Content,
        reply_to: Option<&MessageId>,
    ) -> anyhow::Result<MessageId>;

    /// Download media to a local cache path. Returns path to the file.
    async fn download_media(&self, media: &Media) -> anyhow::Result<PathBuf>;

    /// Mark messages as read.
    async fn mark_read(&self, chat_id: &ChatId, up_to: &MessageId) -> anyhow::Result<()>;

    /// Add a reaction emoji.
    async fn react(
        &self,
        chat_id: &ChatId,
        message_id: &MessageId,
        emoji: &str,
    ) -> anyhow::Result<()>;

    /// Search messages. Returns messages matching the query across this provider.
    async fn search(&self, query: &str, limit: usize) -> anyhow::Result<Vec<Message>>;

    /// Get contact/user info for a platform ID.
    async fn contact_info(&self, platform_id: &PlatformId) -> anyhow::Result<Option<Sender>>;
}
```

```rust
#[derive(Clone, Debug)]
pub enum ProviderEvent {
    /// A new message arrived (or was synced from history)
    Message { message: Message, is_historical: bool },
    /// A message was edited
    MessageEdited { message: Message },
    /// A message was deleted
    MessageDeleted { chat_id: ChatId, message_id: MessageId },
    /// A reaction was added or removed
    ReactionChanged { chat_id: ChatId, message_id: MessageId, emoji: Arc<str>, added: bool, sender: PlatformId },
    /// Read receipt
    Receipt { chat_id: ChatId, message_ids: Vec<MessageId>, kind: ReceiptKind, sender: PlatformId },
    /// Chat list changed (new chat, name change, mute, pin, archive)
    ChatUpdated(Chat),
    /// Auth state changed
    AuthRequired(AuthChallenge),
    AuthSucceeded,
    /// Sync progress (0–100)
    SyncProgress(u8),
    SyncComplete,
    /// Provider disconnected (with optional reason)
    Disconnected(Option<Arc<str>>),
    /// Provider is reconnecting
    Reconnecting,
    /// Typing indicator
    Typing { chat_id: ChatId, sender: PlatformId, is_typing: bool },
}
```

### Task 0.4 — cgo ↔ tokio bridge prototype

`[ ]` **0.4** Prove the cgo callback → tokio async channel bridge in `crates/providers/whatsapp/`

> This is the highest-risk task. It must be done before any provider business logic.

- **Problem:** whatsmeow fires callbacks from Go goroutines (C-exported function pointers). These arrive on non-tokio threads. They must be safely forwarded into a tokio `mpsc` or `broadcast` channel so the async provider code can `await` them.

- **Solution pattern (known to work, used in wstui reference project):**
  - Go calls a `extern "C"` Rust function with raw pointer arguments
  - That function casts the user-data pointer back to `*const Sender<Event>` (the tokio sender, leaked and kept alive)
  - It calls `sender.send(event)` — this is safe from any thread since `tokio::sync::mpsc::UnboundedSender` is `Send`
  - The async provider `recv`s from the channel in its event loop task

- **Prototype files:**
  - `crates/providers/whatsapp/go/go.mod` — module `chat-cli/whatsapp`
  - `crates/providers/whatsapp/go/bridge.go` — minimal: `NewClient`, `Connect`, `SetMessageCallback`, `Disconnect`
  - `crates/providers/whatsapp/go/bridge.h` — C header (generated or hand-written)
  - `crates/providers/whatsapp/build.rs` — same `go build -buildmode=c-archive` pattern as wstui
  - `crates/providers/whatsapp/src/bridge.rs` — `extern "C"` FFI declarations
  - `crates/providers/whatsapp/src/lib.rs` — `WhatsAppProvider` stub + bridge test

- **`build.rs` pattern:**

```rust
fn main() {
    let out = PathBuf::from(env::var("OUT_DIR").unwrap());

        .current_dir("go")
```

- **Bridge test (in `src/lib.rs` under `#[cfg(test)]`):**
  - Calls `new_client()` with an in-memory path
  - Registers a message callback
  - Fires a synthetic event from Go
  - `await`s receiving it from the tokio channel within a 1-second timeout
  - Asserts the message was received correctly

- **Acceptance:** `cargo test -p whatsapp -- bridge` passes on Linux. The test confirms cgo callbacks arrive in the tokio receiver.

### Task 1.2 — Rust WhatsAppProvider

`[ ]` **1.2** Implement `WhatsAppProvider: Provider` in `crates/providers/whatsapp/src/`

- **Files:**
  - `src/lib.rs` — re-exports
  - `src/bridge.rs` — all `extern "C"` declarations + FFI-safe types (mirrors Go)

- **`WhatsAppProvider` struct:**

```rust
pub struct WhatsAppProvider {
    id: ProviderId,
    config: AccountConfig,
    event_tx: broadcast::Sender<ProviderEvent>,
    connected: Arc<AtomicBool>,
    // The tokio mpsc receiver that gets cgo callbacks forwarded to it
    _bridge_task: JoinHandle<()>,
}
```

- **cgo→async wiring in `WhatsAppProvider::new()`:**
  1. Create a `tokio::sync::mpsc::unbounded_channel::<RawEvent>()`
  2. Box the sender and leak it as a raw pointer → pass as `data` to `C_SetMessageHandler`/`C_SetEventHandler`
  3. Spawn a tokio task that loops on `rx.recv()`, converts `RawEvent → ProviderEvent`, and calls `event_tx.send()`
  4. The leaked sender is freed when the provider drops (store the raw pointer, free in `Drop`)

- **`impl Provider` method mapping:**
  - `connect()` → `C_Connect` (streams QR codes via `AuthRequired(QrCode(…))` events)
  - `chats()` → `C_GetContacts` + `C_GetGroupInfo` → construct `Vec<Chat>` (read last_msg from local `Store`)
  - `history()` → query local `Store` (whatsmeow syncs history via events; no separate history call needed for V1)
  - `send()` → `C_SendTextMessage` or `C_SendMediaMessage`
  - `download_media()` → `C_DownloadMedia` to media cache dir
  - `mark_read()` → `C_MarkRead`

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| cgo↔tokio bridge segfaults under load | Medium | High | Prototype in Phase 0.4 before any business logic; fuzz the bridge with synthetic events |
| whatsmeow API changes break Go layer | Medium | Medium | Go layer is one isolated crate; version-pin whatsmeow in go.mod |
| Slack OAuth redirect handling is fiddly on all OSes | Medium | Low | Use a simple local HTTP server; fall back to manual token paste if needed |
| ratatui-image protocol detection wrong in some terminals | Low | Low | Always expose `Ctrl+P` to cycle protocols; default to Unicode block on unknown terminals |
| Windows cgo + MSVC toolchain CI flakiness | Medium | Medium | Test early in Phase 0.5; have MinGW fallback |
| Discord deferred — architecture must not make it hard to add | Low | High | `Provider` trait is the only interface; Discord = new crate implementing it, no other changes |
| Memory leak in cgo callback → channel → async path | Low | High | Run under Valgrind/ASAN in CI; explicit `Drop` on leaked sender |
| Slack user token scope restrictions | Low | Medium | Ensure OAuth app is registered with correct scopes before Phase 3; document app setup |
